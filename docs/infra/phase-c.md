# Phase C — Cloud Dev Environment

Stand-up of the deployed dev environment: Neon Postgres, Fly.io server, Vercel devtools, and GitHub Actions workflows that automatically deploy server and devtools on merge to `main`. Production is deferred — when it ships, it's a second set of resources behind the same machinery, no architectural change.

## TL;DR

Crowd has a fully automated, path-filtered, secret-managed dev deploy environment. Every push to `main` that touches server-relevant code redeploys the Fastify API to Fly.io against a Neon-hosted Postgres; every push that touches devtools-relevant code redeploys the Vite app to Vercel. Migrations run as Fly's `release_command` so a bad migration aborts the deploy before traffic flips.

Live: `https://crowd-dev.fly.dev` ↔ `https://crowd-dev-devtools.vercel.app` ↔ Neon Postgres in `us-west-2`.

## Deviations from the phase prompt and why

1. **Region: `sjc` instead of `sea`.** The prompt assumed Fly had a Seattle (`sea`) region. `fly platform regions` confirms it doesn't — Fly's North America US regions are `iad ord dfw lax sjc ewr`. Picked `sjc` as the closest available colocation point with Neon `us-west-2`. Latency hit vs. true colocation: ~25-30ms RTT. Acceptable for dev.

2. **Reused `fly launch`'s auto-generated `FLY_API_TOKEN`** instead of creating one with `fly tokens create deploy --app crowd-dev -x 999999h`. Same scope (deploy, app-scoped), same effective non-expiry. Avoided one user-side step. The deleted `fly-deploy.yml` workflow that came with the auto-token was discarded; the token wasn't.

3. **Added `apps/devtools/vercel.json`.** Not in the prompt. Required because Vercel CLI's `vercel build` doesn't honor the dashboard's "Build Command" override the same way the GitHub integration does. With the integration disabled, `vercel.json` is the file-versioned source of truth.

4. **Workflow `working-directory` semantics.** The prompt's example `deploy-devtools.yml` used `working-directory: apps/devtools` on each Vercel step. That conflicts with the Vercel project's "Root Directory" setting because the CLI resolves project root as `<cwd>/<rootDirectory>`, double-appending `apps/devtools`. Final form runs from repo root with job-level `VERCEL_ORG_ID`/`PROJECT_ID` env. Documented inline in the workflow file.

5. **C5 surfaced two bundling bugs not predicted in the prompt:**
   - `packages/api` was format-inconsistent (CJS package declaration, ESM-syntax dist). Fixed by aligning the tsconfig and package.json.
   - `commonjsOptions.include` regex matched specifiers, not resolved file paths, so the Rollup commonjs plugin never processed workspace deps. Fixed by changing the regex. This was the *actual* runtime fix; the package-format change was correct but unrelated.

   Both were latent — they only surfaced once the devtools production-bundle path was exercised, which Phase C5 was the first to do.

## Verification: what was tested, and the gap

The deploy machinery was empirically validated through the actual deploy iterations of C4-C7, not through a synthetic post-hoc PR. Specifically:

- **4 deploy invocations exercised**: 1 manual `fly deploy` (C4d), 3 workflow-triggered deploys (C6 first push, C6 vercel.json fix, C6 working-directory fix).
- **3 path-filter scenarios validated**:
  - workflow-file change → triggers its own workflow (`1e156bf`, both fired correctly).
  - devtools-only change → triggers Deploy Devtools alone (`d44225c`, `aebd889`).
  - mobile-only change → triggers neither (`8218500`).
- **Health checks confirmed live** via `curl https://crowd-dev.fly.dev/health` after every server deploy.
- **End-to-end cross-platform flow confirmed live** by loading `crowd-dev-devtools.vercel.app` in a browser and observing it successfully fetching from `crowd-dev.fly.dev`.

**The gap, stated honestly**: the *PR merge* path — feature-branch → PR → CI passes → merge to main → deploys fire — was not exercised in this phase. Every Phase C commit went directly to `main` via admin push (with branch-protection bypass logged). The deploy workflows themselves are merge-event agnostic (`on: push: branches: [main]`), so a merge commit triggers them identically to a direct push. This is verified via equivalent paths, not via a synthetic PR — first real PR after Phase C closes the gap incidentally.

## Things noticed but not fixed (carry-overs)

1. **`apps/devtools` bundle is 578KB / 142KB gzipped.** Acceptable for dev; if it grows, code-splitting via dynamic `import()` is the path. Not a Phase C concern.

2. **`packages/api`'s CJS-only emit.** Works but is the older module format. A future ESM migration of the workspace would simplify Rollup's job, eliminate the `commonjsOptions` config entirely, and make the package consumable from native ESM tooling without conversion. Cross-cutting (server consumes `@repo/shared` directly), so out of scope for any phase that doesn't intend to touch server packaging.

3. **Vercel CLI vs. dashboard build-command divergence.** Documented in `vercel.json` and inline in the workflow comments. If Vercel ever harmonizes these, we could simplify. Until then, `vercel.json` is canonical.

4. **`packages/api`'s build script doesn't run `@repo/shared`'s build first.** The verbose Vercel build command works around this. Phase A's "build-before-typecheck" follow-up (deferred per phase prompt) would address it cleanly with Turbo or similar.

5. **Stray `DATABASE_URL` containing `@base/...`** during the failed C4e seed attempt. Source undetermined after diagnostic sweep. Environment now clean (`env | grep -i database` → empty), no auto-loaders present (no `.envrc`, `.mise.toml`, `.tool-versions`). Closed as transient.

6. **No deploy gating on test pass.** C6 workflows fire on push to main directly; the existing `Test` workflow runs in parallel. A future tightening would make Deploy Server's `needs:` reference Test. Filed as Phase E concern (isolate test-gating bugs from deploy-config bugs).

7. **No deploy notifications.** Workflow status only visible in Actions tab. Slack/email hooks would be straightforward additions when the dev environment becomes the thing real testers hit.

8. **No production resources of any kind.** By design — phase prompt's "no production until production" principle. When production ships, the existing workflows duplicate with two changes per workflow (`--app` for fly, `VERCEL_PROJECT_ID` for vercel) and a parallel set of secrets. No new architecture.

9. **Three Neon password leaks during C3-C4 setup.** All three credentials rotated. A final clean rotation using `read -rs` is the closing action of the phase.

## Phase-close action: final Neon password rotation

Three credential leaks during C3-C4 (via IDE selection-share into chat) were rotated immediately on detection. Because rotation churn keeps re-leaking via the same mechanism, the closing rotation is performed at phase end via `read -rs` so the new DSN never enters chat or shell history:

```bash
# After rotating in Neon console:
read -rs FLY_DB
# paste new pooled DSN, hit enter — silent, no echo, no shell history
fly secrets set DATABASE_URL="$FLY_DB"
unset FLY_DB
# Verify:
curl https://crowd-dev.fly.dev/health
# expect: {"status":"ok"}
```

Phase C closed when this rotation completes and `/health` returns ok.
